# Optional Three.js hybrid integration plan

| Field | Value |
|---|---|
| Status | Deferred backlog direction; no implementation authorized |
| Decision date | 2026-09-06 |
| Backlog | [BACKLOG.md](./BACKLOG.md), V3-417 |
| Primary intent | Let PageTurn books participate in an existing Three.js scene while preserving the high-fidelity semantic V3 reading experience |
| Non-negotiable constraint | The lightweight `@ethical-tech/pageturn-book` V3 SDK must remain usable without installing, downloading, or initializing Three.js |
| First delivery | An isolated prototype after separate approval |

## 1. Decision

PageTurn will evaluate an **optional hybrid Three.js presentation layer**, not a
Three.js rewrite of the reader.

Three.js is a strong candidate for:

- a spatial library room and bookshelf;
- physically modeled covers, boards, spines, hubs, page blocks, and stands;
- scene lighting, shadows, depth, camera movement, and occlusion;
- selecting, lifting, carrying, rotating, opening, closing, and returning a
  book;
- integration into applications that already own a Three.js scene.

The existing V3 runtime remains authoritative for:

- publication loading and bounded chapter loading;
- semantic pagination and source anchors;
- page and spread composition;
- page-turn state and canonical navigation;
- selectable text, links, figures, search, bookmarks, and annotations;
- accessibility, focus, history, and durable reading locations.

This boundary preserves the qualities that distinguish PageTurn from a
rasterized flipbook. Three.js adds a spatial presentation capability around the
book; it does not become a second publication or reader state model.

## 2. Current implementation

PageTurn does not currently depend on or invoke Three.js, React Three Fiber,
WebGL, or a canvas renderer.

The current physical treatment uses:

- semantic DOM pages generated by the V3 reader;
- deterministic page-fold calculations in
  [`page-turn-geometry.ts`](./packages/page-turn-v3/src/page-turn-geometry.ts);
- DOM projection and fold polygons in
  [`page-turn-projection.ts`](./packages/page-turn-v3/src/page-turn-projection.ts);
- CSS perspective, transforms, clipping, gradients, and shadows in
  [`styles.css`](./packages/page-turn-v3/styles.css);
- data-driven shelf volumes in
  [`bookshelf.ts`](./packages/page-turn-v3/src/bookshelf.ts).

The current approach remains the default and fallback even if an optional
Three.js adapter is later introduced.

## 3. Architectural boundary

```text
Publication manifest + semantic chapter HTML
                    |
                    v
       PageTurn V3 reader state
       - pagination
       - canonical location
       - research tools
       - accessibility
                    |
          shared appearance contract
                    |
          +---------+----------+
          |                    |
          v                    v
  Existing DOM/CSS reader   Optional Three.js adapter
  - live semantic pages     - shelf and casework
  - selection and links     - physical book mesh
  - page-turn projection    - lighting and camera
  - canonical reading UI    - pickup/carry transitions
          |                    |
          +---------+----------+
                    |
                    v
       controlled visual handoff
```

`PageTurnResolvedAppearance` remains the single appearance source. The DOM
renderer maps it to CSS variables. A future Three.js adapter maps the same
values to dimensions, materials, textures, roughness, page-block density, and
level-of-detail choices.

## 4. Packaging and dependency isolation

The recommended boundary is a separate optional package:

```text
@ethical-tech/pageturn-book
  - no Three.js dependency
  - current semantic reader and shelf contracts

@ethical-tech/pageturn-book-three
  - optional adapter
  - Three.js as a peer dependency
  - imports the public appearance and bookshelf contracts
```

A separately tree-shakable package is preferred over importing Three.js from
the core package. It provides stronger guarantees that:

- existing consumers do not install or download Three.js;
- current `/v3/`, `/sdk/`, and non-3D shelf routes do not request a Three.js
  chunk;
- applications that already use Three.js reuse their existing compatible
  version instead of receiving a second renderer copy;
- the optional adapter can evolve on a different release cadence;
- a failed or unavailable WebGL context can fall back to the DOM shelf and
  reader.

The repository's prototype route may dynamically import the adapter, but the
default PageTurn entry point must never import it directly or indirectly.

## 5. Existing-scene integration

Integration into an application-owned Three.js scene is the primary use case.
The adapter must not assume that it owns:

- the `Scene`;
- the `Camera`;
- the `WebGLRenderer` or future WebGPU renderer;
- the render loop;
- lighting;
- post-processing;
- orbit or pointer controls;
- global color-management settings.

The host supplies those objects and calls the adapter during its own update
loop. The adapter returns an `Object3D` root and explicit lifecycle methods.

Conceptual API:

```ts
import { createPageTurnThreeAdapter } from
  "@ethical-tech/pageturn-book-three";

const books = createPageTurnThreeAdapter({
  scene,
  camera,
  renderer,
  volumes,
  onOpenBook(volumeId) {
    openSemanticReader(volumeId);
  },
});

scene.add(books.root);

function frame(deltaSeconds: number) {
  books.update(deltaSeconds);
  renderer.render(scene, camera);
}

books.destroy();
```

The production contract will use Three.js types rather than an untyped global
namespace. Three.js should be an adapter peer dependency so the host and
adapter share one object graph and renderer version.

### 5.1 Ownership rules

- The host owns scene, camera, renderer, controls, and the frame loop.
- The adapter owns only objects, geometries, materials, textures, listeners,
  and animation state that it creates.
- `destroy()` disposes every adapter-owned GPU resource and removes every
  listener.
- The adapter does not add lights, alter tone mapping, change renderer pixel
  ratio, or render an extra frame unless explicitly requested.
- Units, up-axis, handedness, color space, and scale are documented.
- Host raycasting may be used through adapter-provided targets and metadata.

## 6. Physical book model

The first reusable book object should be a `THREE.Group` composed from the
existing appearance configuration.

### 6.1 Closed-book geometry

- front and back cover boards;
- rounded or flat spine;
- raised hubs or exposed stitching;
- page block with configurable depth;
- fore-edge finish;
- headbands and tailbands;
- board overhang and corner roundness;
- optional wear and age material parameters.

### 6.2 Open-book geometry

- rigid left and right cover boards;
- binding and gutter;
- left and right page blocks;
- a bounded number of visible resting leaves;
- configurable gutter, bottom, and fore-edge lift;
- an aperture reserved for the live semantic page surfaces;
- simplified mobile and distant-view levels of detail.

The adapter must not create one mesh or texture for every publication page.
Page count affects the physical page-block dimensions and edge treatment, not
the number of live GPU objects.

## 7. Text and surface strategy

### 7.1 Cover and binding text

Short cover, spine, shelf-label, and edition text may be rendered into bounded
canvas textures or another measured texture-atlas implementation.

Requirements:

- generate only the currently needed labels;
- use configured typography and color;
- scale for device pixel ratio within a memory cap;
- dispose superseded textures;
- retain equivalent DOM names and controls for accessibility;
- never fetch remote fonts or imagery implicitly.

### 7.2 Publication page text

Full publication pages remain live semantic DOM. They must not become the
canonical reader as:

- canvas textures;
- `TextGeometry`;
- signed-distance-field glyph meshes;
- screenshots stored as publication pages.

Rasterizing long-form pages would weaken selection, links, search, responsive
repagination, accessibility, source anchors, annotation behavior, and text
clarity at changing zoom levels.

### 7.3 Future DOM surface bridge

High-fidelity reading inside a 3D scene will use a synchronized DOM surface
bridge:

1. Three.js renders the book shell, boards, binding, page block, scene, and
   lighting.
2. The adapter exposes the world-space anchors of the left and right readable
   page planes.
3. The bridge projects those anchors through the active camera.
4. The existing semantic page spread is transformed over the reserved page
   aperture.
5. Pointer, focus, selection, links, and research tools continue to operate on
   the DOM.
6. The existing V3 turn solver continues to own semantic face selection and
   canonical navigation.

The first readable pose should be close enough to camera-facing that a planar
DOM spread remains visually and interactively stable. Arbitrary-angle reading,
WebGL/DOM occlusion, and curved live DOM surfaces are later research topics.

During pickup or rapid transport, the adapter may temporarily use a
non-interactive visual proxy. It must restore the live DOM before the book is
presented as readable and must never expose a raster proxy as the accessible
reading surface.

## 8. Interaction and handoff state

The adapter should use an explicit state machine:

```text
SHELVED
  -> SELECTED
  -> CARRIED
  -> PRESENTING
  -> READING_DOM
  -> CLOSING
  -> RETURNING
  -> SHELVED
```

Rules:

- One owner controls the book transform in each state.
- Canonical reading location does not change during spatial animation.
- The DOM reader is activated only after its page aperture is stable.
- Focus moves to the semantic reader after presentation.
- Closing returns focus to the originating accessible shelf control.
- Reduced-motion mode skips or greatly shortens transport while preserving the
  same state transitions.
- Cancellation, route changes, context loss, and destroy restore a stable DOM
  fallback without orphaned scene objects.

## 9. Accessibility and fallback

The Three.js canvas is never the only way to discover or open a book.

- Keep a semantic list/button representation of every shelf volume.
- Preserve the existing flat keyboard order.
- Mirror visual selection to `aria-pressed` and the existing selection card.
- Provide equivalent non-pointer open and return actions.
- Keep announcements in DOM live regions.
- Respect `prefers-reduced-motion`.
- Fall back to the DOM bookshelf when WebGL is unsupported, context creation
  fails, or context recovery fails.
- Do not duplicate publication text in the accessibility tree.

## 10. Performance and payload constraints

The prototype must measure rather than assume that GPU rendering is an
optimization.

- No Three.js code or network request on core V3 routes.
- Dynamically load the prototype scene only after entering its route.
- Reuse geometries and materials where appearance permits.
- Use instancing for repeated shelf or page-edge structures where beneficial.
- Generate textures on demand and cap texture dimensions and memory.
- Reduce hubs, edge detail, anisotropy, shadow-map resolution, and material
  complexity on low-end devices.
- Suspend scene animation when offscreen or hidden.
- Avoid a permanent second animation loop in host-owned scenes.
- Test renderer context loss and complete disposal.

The adapter bundle, Three.js peer/version policy, GPU memory, startup cost,
frame interval, and long tasks must be recorded before promotion.

## 11. Initial prototype

The first prototype is intentionally narrow and isolated from production
routes.

### 11.1 Scope

- A dedicated experimental route.
- A host-created Three.js scene, camera, renderer, lights, and render loop.
- One shelf bay and three configured books.
- One complete procedural closed book.
- Selection, pickup, free rotation, carry, present, close, and return.
- Cover and spine text textures.
- A front-facing handoff to the existing semantic V3 reader.
- DOM fallback, reduced motion, cancellation, resize, and destroy.
- No change to the default SDK entry point.

### 11.2 Explicitly out of scope

- Replacing the semantic V3 reader.
- Rasterizing a full publication.
- Replacing the current fold solver.
- A deformable page mesh or paper-physics engine.
- Reading at arbitrary camera angles.
- WebXR or spatial-computing support.
- Multiplayer or collaborative shelf state.
- Shipping the prototype as a default library experience.

## 12. Prototype acceptance gates

The prototype may advance only if all of these are demonstrated:

1. Core package consumers do not install or request Three.js.
2. Existing V3 routes retain their current functional and browser matrices.
3. A host-owned Three.js scene can mount and destroy the adapter without a
   second renderer or animation loop.
4. The same appearance input produces recognizably corresponding DOM and 3D
   books.
5. Pickup and return preserve the selected publication identity.
6. The readable handoff preserves book, chapter, anchor, font scale, and
   appearance.
7. Live reading text remains DOM, selectable, linkable, searchable, and
   accessible.
8. Keyboard and reduced-motion paths can select, present, read, close, and
   return a book.
9. WebGL context failure and loss recover to a usable DOM experience.
10. Adapter-owned geometries, materials, textures, and listeners are fully
    released.
11. Desktop and representative low-end mobile frame, memory, startup, and
    long-task results are recorded.
12. The payload report proves no regression on non-3D routes.

## 13. Promotion decisions

After the prototype, review these decisions before production work:

- separate package versus an optional core-package subpath;
- supported Three.js version and peer range;
- WebGL renderer first versus a renderer-neutral abstraction;
- DOM overlay versus CSS3D for the readable surface bridge;
- acceptable readable camera angles;
- occlusion behavior between DOM pages and Three.js objects;
- texture and GPU-memory budgets;
- mobile quality tiers;
- whether open-book carrying needs a temporary texture proxy;
- whether the existing fold projection is sufficient in the presented pose;
- licensing and third-party notice updates.

Promotion requires explicit product approval. Until then, V3 remains the
lightweight semantic SDK and the Three.js work remains a backlog prototype.
